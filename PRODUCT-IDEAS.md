# PRODUCT-IDEAS.md — идеи сервиса `log`

> Что это за файл: каталог всех идей **продукта** — от ближайших до очень далёких — собранный из голосовых заметок владельца. Здесь только «что сервис делает и зачем», без деталей имплементации: архитектура кода живёт в `SPEC.md` и `CLAUDE.md`. Повторяющиеся мысли из разных заметок здесь слиты в одну; к идеям привязаны реальные юзкейсы (опыт с MLflow, разбор блога Сбера о тренировке их LLM). Горизонты помечены тегами: `[сейчас]` — текущие версии v0–v1, `[v2]`, `[v3]`, `[далеко]` — без обязательств по срокам.

---

## 1. Ядро: что такое `log` в одном абзаце

`log` — это toolkit (не фреймворк) для ML-тренировок: «Excel для ML». Две половины одной идеи. Первая: все *стандартные* куски production- и research-кода тренировки — чекпоинты, distributed-обёртки, расписания LR, resume, asserts, конфигурация — которые ничего нового не добавляют, а только нужны «чтобы всё это запустить», сворачиваются в один стандартный интерфейс с одним стандартным набором конфигураций; зашёл внутрь toolkit-а — увидел привычный синтаксис, просто вынесенный из файла тренировки. Тренировочный цикл при этом остаётся у человека: мы его не заменяем, а сокращаем. Вторая: всё, что происходит, логируется сырым и полностью — так, что постфактум можно разобрать любой момент обучения (в том числе механистически) и, что важно, отдать это всё LLM на анализ.

## 2. Принципы продукта

Пять убеждений, из которых выводятся все фичи ниже; каждое — одно предложение сути и одно «почему».

- **Toolkit, не фреймворк.** Пользователь владеет циклом `for batch in loader`; `log` никогда не забирает управление — иначе теряется контроль и понимание, ради которых всё затевалось.
- **«Объявил один раз».** Если ты один раз сказал, что работаешь с CUDA — не нужно повторять это в других местах в других форматах, с другими названиями и синтаксисами; каждое логически обособленное для человека действие — одна команда.
- **Данные = читаемые файлы = таблицы.** Любые данные — человеко- и агенто-читаемые файлы; таблицы в UI отображают файлы; иерархия папок на диске = иерархия экранов; всё предсказуемо.
- **Один тип данных, разные контексты показа.** Список прогонов, элемент модели, элемент датасета и сам проект остаются одним `Table`, но collection, detail-preview и fullscreen editor не обязаны выглядеть одинаково: унификация модели не должна превращаться в рекурсивную таблицу внутри таблицы.
- **Автоматический инсайт.** Раз всё визуализируется само, не надо заранее решать «что визуализировать, чтобы увидеть» — статистические и базовые инсайты получаются бесплатно, ты автоматически видишь больше из своих данных.

## 3. Toolkit-сторона (Python, тренировка)

Группа фич про то, что `log` делает *из кода тренировки*: одна строка в коде ↔ видимое поведение в UI, всегда по одному образцу.

- `[сейчас]` Интеграция с PyTorch; логирование **сырых чисел**, а не запечённых картинок с визуализациями — картинки вообще незачем логировать, если визуализации внутри сервиса.
- `[сейчас]` Гиперпараметры интегрированы: объявил в коде — он уже залогирован; никаких отдельных полей, куда надо руками переносить то, что уже написано (прямой урок MLflow, §9).
- `[v2]` Конфигурация принимается и как Python mapping/dataclass, и как `.json`/`.yaml`/`.yml`: любой вход нормализуется в один `config.json`, поэтому UI, сравнение и воспроизводимость не зависят от того, использует человек обычный словарь, YAML или Hydra-подобный workflow.
- `[сейчас]` Автосохранение и восстановление чекпоинтов и стейта датасета; tqdm в консоли — автоматически из кода. UI и поведение кода связаны.
- `[v2]` Консольные логи как уведомления в UI.
- `[v2]` Кастомные метрики и хуки пользователя: определить свою метрику (пример из практики: compression ratio на BPE-подобном сжатии хвостов последовательностей для ловли зацикливания текста; агрегация вероятности EOS-токена через softmax во время генерации) — и сервис показывает, *где и на каком этапе* она возникает, на «большой карте всего, что происходит». Стандартные вещи (зацикливание и т.п.) определить заранее, но кастом обязателен — пользователь должен понимать, с чем конкретно он работает.
- `[v2]` Базовые диагностические метрики по умолчанию, доступные прямо во время обучения без настройки: что учится, что не выучивается, состояние матриц.
- `[v2]` Автоматические метрики прогонов, генерируемые по уже залогированным данным.
- `[v3]` Свипы и запуск экспериментов один за другим — прямо из интерфейса, без инфраструктурного кода вокруг. Вернее, инфраструктурный код пишется один раз и все. Этот инфраструктурный код просто из тулкита добавляется и все у тебя есть полное управление из веба всем, что происходит.
- `[v3]` Draft/clone workflow: любой run можно клонировать в редактируемый draft, поменять config или input model/checkpoint и выполнить из UI либо командой `log-agent execute --id …`. Исторический run не «сбрасывается» и не переписывается: retry создаёт новый draft, поэтому происхождение результата всегда видно.
- `[v3]` Продвинутые, часто встречающиеся workflow поверх того же boundary: Hydra/OmegaConf-конфиги, sweeps, staged pipelines, resume/fork от checkpoint и запуск evaluation jobs. Они не получают отдельных типов в ядре — config, draft, stage и result по-прежнему таблицы.
- `[v3]` Запуск модели на ручное тестирование (тестовый инференс) из UI.
- `[далеко]` Инструменты для kernel development / оптимизации кернелов.

## 4. Данные, таблицы, тензоры

Группа про сам «Excel для ML»: что можно делать с базовым элементом.

- `[сейчас]` Таблицы вложены в таблицы (проект — просто папка-таблица); ссылки между таблицами независимо от места в иерархии; иерархия определяется тем, *где таблица порождается* — где в экранах добавил, там в папках и лежит.
- `[сейчас]` Внутри ячейки может лежать `table_ref`. В collection-таблице он выглядит как обычная ссылка или компактный preview, но никогда не разворачивает целую интерактивную таблицу с собственным resize. На detail-странице те же ссылки становятся независимыми preview-тайлами; клик проваливает в полную таблицу.
- `[v1]` Редактирование как в Excel / Google Sheets / Apple Numbers: размеры ячеек, добавление/удаление строк-столбцов, агрегация, формулы.
- `[v1]` Базовый spreadsheet-parity, которого ещё не хватает: zoom; find/replace; fill/drag. Ctrl/Shift/drag range selection, range copy/cut, resize строк/колонок, hide/reorder/freeze columns, типизированные фильтры и ordered multi-sort уже работают; view controls не меняют исходную таблицу, Cut остаётся одним undoable edit.
- `[v2]` Pivot-style сводки и группировки строятся через `agg/join` и позже получают визуальный builder. Merge-cells, макросы/VBA и декоративное форматирование не входят в baseline: они не помогают разбирать ML-run и размывают один тип `Table`.
- `[v2]` Язык формул минималистичный, с **иерархической адресацией** вместо C2:D3: путь к таблице через точку + автокомплит списком таблиц (путь + название). Юзкейс: составить временный тензор из первого вектора attention-матрицы первого слоя и второго вектора второго слоя.
- `[v2]` Мердж нескольких таблиц; сначала — только через язык формул (проще и логичнее), отдельный интерфейс мерджа — позже. Custom-таблицы: merge двух других или таблица со ссылками в ячейках.
- `[v2]` Фильтрация и выбор по всем-всем параметрам среди большого количества прогонов; множественное умное переименование проектов.
- `[v3]` Ручное редактирование тензоров — спорно, но оставить как универсальную функцию (выключим в важных местах): вписать свои данные/столбцы, манипуляция прямо на графике (соединить точки — присоединить два тензора). Весёлый юзкейс: вручную занизить softmax на выходном слое LLM во время генерации одного токена на тестовом инференсе.
- Фиксированные обозначения поверх унифицированного вида: «таймлайн» = шаг обучения, «модель» = computation-граф всей модели — оставить, даже при едином внутреннем типе.

## 5. Визуализация и UI

Группа про то, как всё это показывается; каждый пункт — один паттерн отображения или взаимодействия.

- `[сейчас]` Красивый UI, запускается локально; SPA; выглядит как обычный простой трекер экспериментов — проваливаешься по иерархии таблиц, никакой другой навигации.
- `[сейчас]` Представление таблицы переключается: сетка ячеек ↔ график — та же структура, разный вид.
- `[сейчас]` Три режима композиции поверх одного `Table`: **collection** — одна полноширинная таблица со ссылками; **detail** — именованная секция с независимыми preview-тайлами в flex-wrap сетке; **editor** — fullscreen после Expand. Полноценная таблица не вкладывается в ячейку другой полноценной таблицы.
- `[сейчас]` У каждой collection/detail/editor-таблицы есть собственный `Filter rows…` и active-filter chips. Глобальный `Go to table…` продолжает искать сущности и пути, поэтому не маскируется под фильтр текущей таблицы.
- `[сейчас]` Заголовок колонки даёт resize, sort и filter; Shift-click добавляет вторичный sort. Ширина/высота, ordered sorts, фильтры, выбор/порядок и frozen prefix колонок кодируются в URL и могут быть расшарены.
- `[v1]` Detail-секция имеет имя, счётчик и разделитель; её тайлы переносятся по строкам, drag-reorder меняет их порядок, resize меняет размер preview, а Expand открывает editor. Пустые, loading и error состояния занимают ту же секцию и объясняют следующий шаг.
- `[v1]` Быстрый скролл по графикам из списка клавишами-стрелками.
- `[v1]` Мелкие паттерны графиков: hover показывает значение в точке; клик фиксирует линию; можно вбить точное значение; числа округлены, при наведении раскрываются полностью — оверлеем, не двигая таблицу.
- `[v1]` График сохраняет стандартные plot controls: zoom/pan, выбор шкалы, toggle легенды; один клик по серии скрывает/показывает её, двойной оставляет только её. Эти действия меняют представление, а не исходные данные.
- `[v2]` Склеивание нескольких графиков продольно, если прогон прервался.
- `[v2]` Иерархичная лог-консоль: блоки-карточки логов в ряд, соединённые тонкими кривыми сверху вниз — иерархия есть, но это всё ещё обычная удобная лог-консоль, а не дерево вычислений.
- `[v2]` Tree-like plots (мокап): тайлы-графики, соединённые тонкими уголками-коннекторами родитель→дети — та же идея иерархии карточек, но для графиков; родительский тайл подсвечен акцентом.
- `[v2]` Преувеличенный «hero»-масштаб текущей сущности (мокап main logs screen): огромный заголовок и график во всю ширину, таймлайн эпох под ним; всё второстепенное — тонкое и серое; одна акцентная краска поверх нейтральной шкалы.
- `[v2]` Вложенные логи: папки с графиками, а не всё в одну кучу (наблюдение по количеству логов у bandwidth research).
- `[v2]` **Zoom in / zoom out** как философия: вместо того чтобы каждый раз приближать деталь, можно отдалиться, но очертания деталей протягиваются на уровень выше — например скаляр-метрика переводится в цвет. Конкретика: прямоугольник, поделённый на стадии пайплайна, каждая стадия окрашена спектром красный→зелёный по значению метрики; показывается при выполнении условий на значение.
- `[v2]` Replay: пошаговый управляемый график изменений, воспроизведение того, что и когда поменялось; собственный формат последовательности снимков с траекториями — как анимация хода обучения.
- `[v2]` Таймлайн обучения модели: посмотреть значения любой её части в любой момент времени.
- `[v3]` Экспорт финальных графиков в высоком разрешении, в любых стилях, для научных работ; экспорт всеми библиотеками с визуальными настройками; гифки и видео изменения графиков во времени.
- `[v3]` Мобильная версия для трекинга экспериментов; три раскладки: компьютер, iPad, телефон.
- `[v3]` Унифицированный способ рендеринга всех деталей ради отзывчивости при перемещении между кучей графиков; минимальные анимации в интерфейсе — потом, чтобы сначала сохранить минималистичность.

Проверенные паттерны, которые стоит заимствовать без переноса чужой объектной модели: [ClearML Task Table](https://clear.ml/docs/latest/docs/webapp/webapp_exp_table/) разделяет глобальный search и фильтры колонок, сохраняет width/order/sort/filter в URL; [W&B Runs](https://docs.wandb.ai/models/runs/filter-runs) строит типизированные filter expressions, а [W&B panels](https://docs.wandb.ai/models/app/features/panels) отделяет переставляемую dashboard-сетку от таблицы прогонов; [MLflow Tracking](https://mlflow.org/docs/latest/tracking) держит run listing/search и comparison как отдельные пользовательские действия. Для `log` это подтверждает один flow: найти проект → отфильтровать/выбрать runs → открыть run → расположить preview-панели → Expand только нужной таблицы.

## 6. Инспектинг модели и интерпретируемость

Группа про заглядывание внутрь модели — то, ради чего логируется всё сырое.

- `[v2]` Визуализация архитектуры модели и размерностей данных.
- `[v2]` PyTorch computation graph — в том числе отдельно для каждого тензора; соединение тензоров стрелочками — отдельный UI.
- `[v2]` Встроенные преобразования для интерпретируемости: PCA, SVD, SAE — и к логам модели, и к датасету на входе: как хочешь крути-верти.
- `[v3]` Обзор кода по тензорам: смотреть, что куда идёт и во что преобразуется — чтобы точно ничего не напутать. Мотивация: огромная доля ошибок в экспериментах — от слабого понимания того, что реально происходит внутри.
- `[v3]` Loss landscape visualizations.

## 7. Сравнение прогонов и пайплайны стадий

Группа из разбора блога Сбера: эксперименты — это не плоский список, а стадии (pretrain → stage 1.5 → SFT → DPO), и сравнивать надо *по стадиям*.

- `[v2]` Раскладка экспериментов не просто сверху вниз, а по этапам пайплайна (по файлам или иначе): визуально видно, где, когда и что использовали; вариации каждого этапа можно соединять с вариациями других и смотреть комбинации. Юзкейс: Сбер замерял метрику CYCLES после каждого этапа пайплайна, чтобы найти, где рождается проблема зацикливания.
- `[v2]` Сравнение прогонов с разными гиперпараметрами по метрике: confusion matrix / матрица похожести, вынесение метрики «наверх», фильтрация по значениям и типам гиперпараметров.
- `[v2]` Multi-select строк run-таблицы складывает выбранные запуски в одну нижнюю comparison-панель. Compare показывает всё сопоставимое в трёх обычных таблицах: diff config/params, same-name metrics aligned by step и дерево результатов/artifacts/debug samples; это один derived `Table`, а не отдельный экран со своей моделью.
- `[сейчас]` Фильтры, ширины колонок и последовательность сортировок кодируются в URL. Закладка восстанавливает вид, а отправленная ссылка открывает у коллеги ту же конфигурацию без отдельной сущности «saved dashboard». `[v2]` Добавить туда выбор и порядок видимых колонок.
- `[сейчас]` Сортировка по заголовку поддерживает вторичный и последующие ключи через Shift-click; индикаторы `↑1`, `↓2` показывают направление и порядок ключей, чтобы результат не был скрытой настройкой.
- `[v2]` Быстрые графики зависимостей: автоматизировать поиск зависимостей вида «средний loss от длины последовательности». Юзкейс: Сбер поймал оверфит DPO на длинных примерах и ввёл экспоненциальный decay веса токенов — такую зависимость надо уметь построить в пару действий.
- `[v2]` Метрика времени эксперимента + утилизация карт как динамическая инфографика: применил умную оптимизацию (sequence packing, dynamic SP…) — увидел, какое изменение она принесла, рядом с метриками качества.

## 8. Инфраструктура и распределённая тренировка

Группа про железо и параллелизм: мониторить можно всё, что угодно, — от одной GPU до фермы.

- `[v2]` Данные о загрузке железа: утилизация множественных GPU/CPU и их линков, визуализации.
- `[v3]` Именованные очереди планируют выполнение draft-задач; workers с `log-agent` забирают задачи из назначенных очередей. Бюджет ресурсов задаётся тем, какие workers подписаны на какую очередь, поэтому одна модель покрывает локальную машину, GPU-пул и разные политики приоритета.
- `[v3]` Трекинг инфраструктуры на системах с огромным числом видеокарт: визуализация логов NVIDIA-стека; сколько куда данных подаётся, где простои, не перемешиваются ли потоки данных; корреляционный анализ — прямо в интерфейсе, операцией из дропдауна над таблицей (все такие логи тоже лежат таблицами).
- `[v3]` Трекинг состояния параллельности обучения: RL, векторизованные среды, системы подачи данных в модель. Юзкейс-нюанс из Сбера: при sequence parallelism в SFT для sequence auxiliary loss (балансировка экспертов MoE) простого all_reduce мало — нужно взвешивать среднее по числу токенов с каждого ранга; паддинги SFT тоже должны учитываться в статистике балансировки. Сервис должен уметь показывать такие parallelism-aware статистики честно.
- `[v3]` Сложные тренировки с кучей чекпоинтов: прерывания, спайки, проблемы — всё видно.

## 9. Уроки MLflow — анти-требования

Список того, что в MLflow было больно, переформулированный в требования к `log`. Общая мысль: непонятность иерархии и разорванность кода и UI — главный враг.

- Папки с кириллицей и пробелами работают; место, откуда читаются данные, видно в UI и легко задаётся из Python API — никаких «писал в глобальную папку, а на сервере пусто».
- Незакрытый прогон закрывается сам (тихий или громкий fallback), а не висит вечно.
- Понятная иерархия настройки: не должно быть загадкой, почему имя эксперимента пишется в файле цикла и что к чему относится.
- Никакого зоопарка «картинки / артефакты / логи / ещё что-то» в разных вкладках: либо логируется автоматически, либо это просто артефакт; всё легко видно в одном интерфейсе. Не должно быть повторяющихся непонятных вкладок, пустых полей и дропдаунов без назначения.
- ClearML-паттерн отдельных Results tabs не копируем: logs, artifacts, metrics и debug samples остаются дочерними `Table` в одной файловой и UI-иерархии, поэтому общий drill/render/search работает для всех результатов одинаково.
- ClearML reset-to-draft не копируем как мутацию: завершённый или упавший run неизменяем, а «retry as draft» явно форкает его config/input model в новый draft. Это сохраняет воспроизводимость и историю попыток.
- Статус прогона очевиден без консоли: на каком шаге, сколько всего шагов, завис или нет.
- Производительность UI священна: графики не обновляются с опозданием и не показываются наполовину, а такого "быть не должно вообще никогда".
- Multi-user вид (когда появится, §10): хранилище, эксперименты и «кто что сейчас делает» — в одном месте, а не по разным страницам; видно, что это один и тот же человек (хэндл = почта = его эксперименты), zoom out на всю картину и zoom in к деталям.

## 10. Многопользовательность и enterprise

Группа далёких горизонтов про команды и большие компании.

- `[v3]` Многопользовательский режим: доступ многим людям, видно, кто что делает (см. §9 про единый вид); аккаунты и логины пользователей.
- `[далеко]` Большое хранилище для больших компаний: логировать все состояния модели во время тренировки, с доступом к хранилищу.
- `[далеко]` MCP-сервер, консольный доступ ко всему этому — чтобы агенты работали с данными сервиса напрямую.
- `[далеко]` Полный автоматизированный пайплайн тренировки и деплоя моделей с онлайн метриками качества, как ClearML.

## 11. Документация, блоги, open source

Группа про то, как продукт объясняет сам себя; аудитории разные — материалы разные.

- Документация **для агентов** и skill-файлы; документация **для LLM** с точными описаниями, как что делать.
- Документация **для новичков**: вплоть до «что такое декораторы в Python» и базовых техник PyTorch.
- Документация **для профессионалов**: с отсылками к MLflow и другим сервисам и сравнениями.
- Философия кода как публичный материал: код делится на идентичные reusable-компоненты, их число сокращается, креатив только там, где он есть; без boilerplate, каждая строка имеет высокоуровневое значение; человек без агента разбирается, не теряясь в контексте, и двигается по нему иерархически.
- Диаграммы всей системы (позже — с минимальными анимациями); схема всех элементов; файловая структура «фича = папка», вложенность файлов отражает вложенность фич.
- Демонстрация «как toolkit сокращает код»: берём код на несколько тысяч строк и цветом подсвечиваем, какие части заменяются какими командами и как каждую потом кастомизировать.
- Гайды на контрибьюцию: как дополнять open-source клиент и API, как делать pull requests, чёткое объяснение структуры добавления новых фич и их проверки — в визуализациях.
- Формулировка философии наружу: toolkit для упрощения понимания кода, быстрых итераций и меньшей неопределённости, которую вносят языковые модели; плюс способ увидеть больше из данных (§2, автоматический инсайт).
- Граничный API для добавления своих визуализаций «в своём стиле»: через LLM прямо в коде или в окошке-редакторе в веб-интерфейсе.
